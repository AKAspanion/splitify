# SQL Connect and Firebase Auth Foundation Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: the project's workflow policy names the executor (`run.executor`): ga:implement-with-subagents by default, or ga:implement. Follow the policy and this plan's Checkpoints. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Stand up Splitify's SQL Connect schema and operations, with every access rule tested on the emulators, plus Firebase Auth in the browser and the contact-merge function, without changing the running app.

**Architecture:** One SQL Connect service, `splitify`, in `asia-south1`, with one schema and two connectors: `app`, whose operations the browser calls under `@auth(level: USER)` with membership checked inside each operation, and `admin`, whose `NO_ACCESS` operations only Cloud Functions call. Each slice of operations lives in its own `.gql` file in a connector folder, with its rule tests beside it, run against the Auth and SQL Connect emulators. Firebase Auth runs in the browser from `lib/firebase/`; a 2nd-gen Cloud Function triggered by `UpsertMe` merges a contact into a verified new account.

**Tech Stack:** Next.js 16 App Router, React 19, TypeScript 6.0, yarn 1, Vitest 5. Firebase JS SDK (`firebase`: `firebase/app`, `firebase/auth`, `firebase/data-connect`), Firebase SQL Connect on Cloud SQL for PostgreSQL with SDKs generated by `firebase dataconnect:sdk:generate`, `firebase-admin` and `firebase-functions` (2nd gen) on Node 22, the Firebase CLI on the PATH (`firebase` 15.x) for the emulators. The app itself still runs on Prisma 7 and Clerk 7 until spec 2. The repository has no CI.

**Spec:** [docs/specs/2026-11-04-sql-connect-foundation.md](../specs/2026-11-04-sql-connect-foundation.md)

## Global Constraints

- Project `splitify-416321`; SQL Connect service id `splitify`, location `asia-south1`; Cloud SQL instance `splitify-fdc`, database `fdcdb`; Cloud Functions region `asia-south1`.
- Nothing is deployed and nothing runs against the real project: every test runs on the emulators. Deploying, and enabling APIs, wait for the developer.
- Nothing under `app/`, `actions/`, `components/`, `hooks/`, `store/`, `prisma/` or `proxy.ts` changes: the app keeps running on Prisma and Clerk.
- A record the caller may not see answers exactly as a missing one does: `null` from a query, and the `@check` message `"Not found"` from a mutation.
- Ids and emails of the caller come from the token (`auth.uid`, `auth.token.email`), never from variables.
- Every `UUID` key is passed in by the caller (made with `crypto.randomUUID()`); an insert with an existing key fails and changes nothing.
- Input limits: titles and names at most 100 characters, descriptions at most 500, emails at most 254, amounts greater than 0 and at most 10,000,000, at most 50 payments and 50 splits per expense.
- Emails are stored trimmed and lower-cased.
- Logs (functions) carry the operation and the cause class, never a token, an email or a request body.
- Generated SDKs are written to `dataconnect/generated/` (ignored by git) and imported as `@dataconnect/app` and `@dataconnect/admin` through `tsconfig.json` paths and the Vitest alias.
- Rule tests sit beside the `.gql` file they test, as `<name>.test.ts`, and run only through `yarn test:rules`, as do `functions/` and `lib/firebase/` tests, which need the emulators; `yarn test` excludes all three.
- Installs run with `--ignore-scripts`: `postinstall` runs `prisma db push`. Run `npx prisma generate` and `yarn dataconnect:generate` after an install instead.

## Checkpoints

None: the policy's `run.checkpoints` is `none`, and the spec asks for none. The run stops only at the end, before pushing.

The schema, in `dataconnect/schema/schema.gql` (shape only; directives such as `@table`, `@ref`, `@unique` and `@default(expr: "request.time")` as SQL Connect spells them):

```graphql
enum ExpenseType { EQUAL EXACT PERCENT }
enum ExpenseTag { EXPENSE SETTLEMENT }
enum ActivityType { SETTLEMENT_MINUS SETTLEMENT_PLUS EXPENSE_MINUS EXPENSE_PLUS EXPENSE_UPDATE MEMBER_MINUS MEMBER_PLUS GROUP_MINUS GROUP_PLUS GROUP_UPDATE SYSTEM USER }

type User @table(key: "id") { id: String! email: String! @unique name: String firstName: String lastName: String imageUrl: String signedUp: Boolean! createdAt: Timestamp! updatedAt: Timestamp }
type Group @table(key: "id") { id: UUID! title: String! description: String imageUrl: String type: String currency: String! mute: Boolean! createdAt: Timestamp! updatedAt: Timestamp }
type GroupMember @table(key: ["group", "user"]) { group: Group! user: User! createdAt: Timestamp! }
type Friendship @table(key: ["user", "friend"]) { user: User! friend: User! createdAt: Timestamp! }
type Expense @table(key: "id") { id: UUID! amount: Float! currency: String! description: String! category: String type: ExpenseType! tag: ExpenseTag! group: Group! creator: User! createdAt: Timestamp! updatedAt: Timestamp }
type UserPayment @table(key: "id") { id: UUID! amount: Float! user: User! expense: Expense! }
type UserSplit @table(key: "id") { id: UUID! amount: Float! percent: Float user: User! expense: Expense! }
type Activity @table(key: "id") { id: UUID! type: ActivityType! actor: User! group: Group subject: User expenseId: UUID amount: Float title: String! createdAt: Timestamp! }
type Feedback @table(key: "user") { user: User! title: String! description: String createdAt: Timestamp! updatedAt: Timestamp }
type AuthnDevice @table(key: "user") { user: User! devices: Any! createdAt: Timestamp! updatedAt: Timestamp }
```

`currency` defaults to `"inr"`, `Group.mute` to `false`. Deleting a group removes its members, expenses (with their payments and splits) and activity; deleting an expense removes its payments and splits. Use the schema's cascade if SQL Connect offers one; otherwise the deleting mutation removes the children first, in its transaction.

Operations in `dataconnect/app/expense-writes.gql` (each `@auth(level: USER) @transaction`):

| Operation | Variables | Returns | Refused with |
|---|---|---|---|
| `CreateExpense` | `id: UUID!, groupId: UUID!, amount: Float!, description: String!, category: String, type: ExpenseType!, payments: [{ id: UUID!, userId: String!, amount: Float! }!]!, splits: [{ id: UUID!, userId: String!, amount: Float!, percent: Float }!]!, activityId: UUID!` | `expense_insert` key | `"Not found"` (caller not a member), `"Only members of this group can be added to an expense"` (a payer or splitter not a member), a limit message |

`CreateExpense` writes `creator` and the activity's `actor` from `auth.uid`, `tag: EXPENSE`, and an `Activity` with `type: EXPENSE_PLUS`, `group`, `expenseId`, `amount` and `title` = the description. `CreateSettlement` writes `tag: SETTLEMENT`, `type: EXACT`, `description: "Settlement"`, one payment by `fromUserId`, one split to `toUserId`, and `Activity` `SETTLEMENT_PLUS` with `subject` = `toUserId`.

Operations in `dataconnect/admin/devices.gql` (`@auth(level: NO_ACCESS)`): `GetDevices(userId: String!)` returns `authnDevice { devices }` or `null`; `SaveDevices(userId: String!, devices: Any!)` upserts it.
