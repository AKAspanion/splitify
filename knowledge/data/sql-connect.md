# SQL Connect schema and connectors

The database chosen in [Store data in Firebase SQL Connect](../decisions/sql-connect-database.md). The Prisma schema in
[data model](model.md) is what the running app still uses until the app moves over; this is the schema it moves to.

## Tables and keys

The tables are in `dataconnect/schema/schema.gql`: `User`, `Group`, `GroupMember`, `Friendship`, `Expense`,
`UserPayment`, `UserSplit`, `Activity`, `Feedback`, `AuthnDevice` and `PushToken`. Read the file for fields and enums; what it can't
say:

- Every UUID key is passed in by the caller, never generated by the database, so a client can queue a write offline
  with its ids already fixed.
- UUIDs read back from the database come without hyphens.
- `User.email` is `@index`, not unique: a contact and the account that later signs up with its email share the email
  until the merge ([contact identity](../domain/contact-identity.md)).
- A person's `User.id` is their Firebase uid; a contact has `signedUp: false` ([users](user.md)).
- Deleting a required reference cascades: an expense takes its payments and splits, a group takes its members and
  expenses. `Activity.group` is optional, so deleting a group sets it to null instead of deleting the activity.

## Connectors

In `dataconnect/dataconnect.yaml`, one folder each:

- `app` (`dataconnect/app/`): what a signed-in person does, with a generated SDK in `dataconnect/generated/app`. It includes `RegisterMyPushToken` and `RemoveMyPushToken` (`push-tokens.gql`): a token is keyed by itself, belongs to whoever is signed in on that device now (registering one another person holds moves it), and removal deletes only the caller's own.
- `expense` (`dataconnect/expense/`): `CreateExpense` and `CreateSettlement`. It has no generated SDK because the
  generated web SDK refuses a variable of a `*_Data` input type, and writing payments and splits in one go needs
  `[UserPayment_Data!]!`. Callers use `mutationRef(dc, "CreateExpense", variables)` from `firebase/data-connect`.
- `admin` (`dataconnect/admin/`): operations with `NO_ACCESS`, which only the admin SDK in Cloud Functions can run
  (devices, the contact merge, and `ListPushTokens` and `DeletePushTokens` for the push functions).

## How access is written

- Rules are `@auth(expr: ...)`, not `@auth(level: USER)`: the level can't be combined with an expression, so each
  expression states what signed-in means (a token that isn't anonymous) and then the limits.
- Membership is checked in the same `@transaction` as the write, with `@check` on a `query @redact`.
- An optional variable in an expression is guarded with `!has(vars.x) || ...`.
- Who may do what is [group member permissions](../decisions/group-member-permissions.md); [roles](../security/roles.md)
  says which files enforce each rule.

## Operation shapes that differ from what you'd guess

- `AddFriend` takes `withGroup: Boolean!`, which must equal whether `groupId` is set.
- `GetGroup` returns `groups`, a list of 0 or 1; `DeleteGroup` returns the group's `title` and `memberIds` as objects with a `userId`, read before the delete, so the push function can name the group.
- A nullable single read is `x(first: { where })`; there is no `*_count` root field, so counts are `_count` inside a
  list.
- `ListMyGroups.search` is a case-insensitive regular expression capped at 100 characters: callers escape it.
- `limit` on `ListGroupExpenses` and `ListMyActivity` is not capped.

## The client data layer

`lib/data/` is what screens call instead of the generated SDK directly: `client.ts` (`dc()` and `queryKeys`, an
explicit list of the app's queries, kept in step with the `.gql` files by a test), `errors.ts` (`toUserMessage`, the
people-facing text for a failure), `search.ts` (`escapeSearch`, for `ListMyGroups.search`'s regular expression) and
`expense-writes.ts` (`createExpense` and `createSettlement`, typed wrappers over `mutationRef` that add `expenseId`
to each payment and split row themselves).

`lib/data/` also holds one file per area, each exporting TanStack Query hooks over the generated SDK and the invalidation a
write needs: `groups.ts`, `expenses.ts`, `people.ts`, `activity.ts`, `feedback.ts`, `profile.ts`, and `ledger.ts`
(the balances adapter, [balances](../features/balances.md)). Every generated query is called with `FRESH` from `client.ts`
(`fetchPolicy: "SERVER_ONLY"`): the SDK's default `PREFER_CACHE` answered a query it had run before from its own copy
and showed stale data after a write, and TanStack Query is the cache. `GetGroupLedger` returns each expense's `type`,
because the split engine needs `EQUAL` apart from `EXACT`.

## Tests

The rules are tested on the Auth and SQL Connect emulators ([run locally](../operations/run-locally.md)), in
`*.test.ts` beside each `.gql` file, with helpers in `dataconnect/test-utils/emulator.ts` (`resetDatabase` clears `PushToken` before `User`, since a token references its user). The expense writes' emulator test is `lib/data/expense-writes.rules.test.ts`, run only by `yarn test:rules`.
