# CI and deploy workflows

The reasons are in [the decision](../decisions/ci-cd-functions-deployed-by-hand.md); the one-time console steps are in
[deploy setup](deploy-setup.md). The files in `.github/` hold the exact commands, versions and pinned action SHAs.

## What runs, and when

- `.github/workflows/ci.yml`: on every pull request, and callable by `deploy.yml` (`workflow_call`). One job installs
  with pnpm (`pnpm/action-setup` pinned to a commit, `pnpm install --frozen-lockfile --ignore-scripts`; `functions/` has its own lockfile) (the SQL Connect SDK is generated by its own step), then runs the format check, lint, type check, unit tests,
  the SQL Connect rule tests, the root and `functions/` audits, the functions build, and the build
  (`pnpm build`, then `pnpm check:hosting` on the Hosting emulator), so a page that stops exporting fails the pull request. Node comes from `.nvmrc`.
  Two more jobs run beside it: a dependency review of the pull request (fails on moderate and above), and the
  end-to-end tests (`pnpm test:e2e`, Chromium, the emulators; see [run locally](run-locally.md)).
- `.github/workflows/secrets-scan.yml`: TruffleHog on pull requests and pushes to `main` for the commits each brings,
  and weekly over the whole history; it fails only on a credential verified against its provider.
- `.github/workflows/codeql.yml`: CodeQL on pull requests, on pushes to `main` and weekly, for the code and for the
  workflows themselves.
- `.github/dependabot.yml`: weekly grouped minor and patch updates for the root, `functions/`, the Android Gradle
  wrapper and GitHub Actions; major bumps of TypeScript and `@types/node` are ignored.
- `.github/workflows/deploy.yml`: on push to `main`, runs CI (all its jobs, e2e included, gate the deploy), then builds the site and deploys it to Firebase Hosting (`FirebaseExtended/action-hosting-deploy`, channel `live`). It doesn't deploy the Cloud Functions, which a project owner deploys by hand ([decision](../decisions/ci-cd-functions-deployed-by-hand.md)). It installs the root dependencies with `--ignore-scripts` for the build, and then runs `pnpm dataconnect:generate` itself, as `ci.yml` does: `next build` typechecks the whole project, which imports the generated SQL Connect SDK. Started by hand with
  `deploy_dataconnect` ticked, it also deploys the SQL Connect schema and connectors. It runs one at a time
  (`concurrency: deploy-production`, never cancelled), checks its settings first and fails naming the missing ones, and
  removes the service-account key file in a step that always runs.

## The audits fail on moderate and above

Both audit steps in `ci.yml` run `pnpm audit --audit-level moderate` (the root one and `pnpm --dir functions`), with
no `--prod`, so dev dependencies count. Advisories with no patched release on the major a dependent asks for are closed
by scoped `overrides` in `pnpm-workspace.yaml` ([debt](../risks/debt.md)). The deploy's `firebase-tools` is pinned to
`15.35.0` (`deploy.yml`).

## Repository settings the deploy reads

- Secret `FIREBASE_SERVICE_ACCOUNT`: the JSON key of the `github-deploy@` service account.
- Variable `FIREBASE_PROJECT_ID`: the Google Cloud project.
- Optional variable `NEXT_PUBLIC_GOOGLE_ADSENSE_ID`: a public value the build reads when set ([the web app](../apps/splitify.md)).
- The functions' secret `SESSION_PASSWORD` is not a repository setting: it is a Firebase secret, set once in the project ([deploy setup](deploy-setup.md)).
- Variables `NEXT_PUBLIC_FIREBASE_API_KEY`, `NEXT_PUBLIC_FIREBASE_AUTH_DOMAIN`, `NEXT_PUBLIC_FIREBASE_PROJECT_ID`, `NEXT_PUBLIC_FIREBASE_APP_ID` and `NEXT_PUBLIC_FIREBASE_VAPID_KEY`: the web config the build bakes in; CI falls back to demo values when they are unset (see `ci.yml`, `deploy.yml`).
- Optional variable APP_URL: shown on the `production` environment; defaults to `https://splitify.spanion.in`.
